# إصلاح بدائل الأدوات — الإصدار 3.1

٢٢ أكتوبر ٢٠٢٦. أصلحنا السببَين السابقين واختبرنا صياغات جديدة، مع ثبات النموذج والأوزان والعتبات. اعتُمد الإصلاح داخل تجربة التطبيق المحلية المقيدة بأربع فرص؛ التفعيل العام ما زال معطلًا.

## الإصلاح

- أصبحت قائمة ألفاظ الطلب والنص تستخدمان التطبيع نفسه؛ لا تختلف «على» و«علي» والتشكيل في المطابقة، مع حفظ النص الأصلي والاقتباسات.
- «تجربة الأداة ضمن فرصة للتعلم» تمثل هدف تعلم وطريقة تجربة. لا يتحول طلب التجربة وحده إلى طلب تعلم.
- توحيد «بشكل عملي» إلى «عمليًا» يحفظ شرط التطبيق العملي. يبقى ما بعده من مدينة أو تخصص أو وصف كما هو، مع اقتباس العبارة وموقعها.
- يظل القبول الجديد مشروطًا بدرجة نموذج ناجحة ومتطلبات الطلب الأصلي والأدلة. لم نحذف قيدًا أو نرفع فرصة لمجرد تطابق اسم الأداة.

## القياس

| المجموعة | الصحيح المقبول | الإضافات الخاطئة | الطلبات المناسبة ذات النتيجة |
|---|---|---|---|
| التطوير — النسخة 2.0 | 142 / 152 | 0 | 121 / 129 |
| التطوير — الإصلاح 3.1 | 145 / 152 | 0 | 123 / 129 |
| الاختبار الجديد — الطريقة الأصلية | 0 / 12 | 0 | 0 / 8 |
| الاختبار الجديد — الإصلاح 3.1 | 12 / 12 | 0 | 8 / 8 |

التطوير يضم ٢٠٥ طلبات مكشوفة، منها خمسة للمراجعة؛ مقاييس البحث تخص ٢٠٠ طلب. رجعت الفرص الثلاث التي فاتت في الطلبين السابقين، ولم نفقد أي صحيح كان الإصدار 2.0 يقبله. بقيت سبعة مرشحين وستة طلبات مناسبة من الموضوعات والصياغات الأخرى دون نتيجة؛ هذا الإصلاح لا يحسم جودة النظام العامة.

الاختبار الجديد: ١٦ صياغة ثبتت قبل تشغيلها، منها ثمانية مناسبة وأربع دون مرشح مناسب وأربع للمراجعة. استرجع الإصلاح المرشحين الصحيحين الاثني عشر، بلا إضافات خاطئة، وبلا أخطاء في قراءة البدائل والمراجعة. هذه نتيجة العينة المختبرة؛ التصنيفات يدوية من منفذ التجربة، والمرشحون الستة عشر أنفسهم. لا يعد هذا تحكيمًا بشريًا مستقلًا أو اختبار استرجاع الألف إعلان أو شروط القبول.

أُبقي الإصدار 3.0 محفوظًا: أصلح الطلبين لكنه فقد مرشح Excel إضافيًا، فلم يشغل الاختبار الجديد. مجسات توحيد الوصف العملي تطوير مكشوف فقط. اختبرنا 3.1 بعد تثبيت كوده وبياناته، ولم نعدلها بعد الاطلاع على النتيجة.

## الربط والتشغيل

ينفذ `workflow.py` الإصلاح فقط داخل تجربة البحث الاختيارية. يتحقق أولًا من موافقة مرتبطة ببصمات النسخة المقاسة وتقاريرها ومقاطع المصادر والعتبات، ثم يسجل كل مرور للنموذج. يبقى الطلب الأصلي وفرعان حدًا أقصى، وتفحص المهلة قبل وبعد كل مرور. ترتيب المرشحين يستخدم الدرجة المقبولة من الأصل أو الفروع، دون عرضها كنسبة للمستخدم.

فحوص القيود والأهلية والأسئلة وإعادة فحص نسخ الأدلة تظل بعد الصلة. فرصة SQL في مجموعة التقييم لا تصبح فرصة مخزنة في التطبيق؛ مخزن التطبيق يضم أربع فرص فقط. نقص تكلفة فرصة Excel يمنع تأكيد المجانية، والأهلية وفتح التسجيل يظلان غير مؤكدين عند نقص الأدلة.

نجح ١٥٠ اختبار خلفية و١١ اختبار تجارب. البوابة العامة `/ready` تبقى 503؛ لا تحول نتيجة العينة المحلية إلى جاهزية إنتاجية.

## التحقق من الواجهة إلى الرد

القصة التي فحصناها: يكتب المستخدم طلب أدوات بديلة، فتصل خطة الطلب إلى البحث المحلي وفاحص الصلة والفروع والقيود والأهلية، ثم تُعرض نتيجة موثقة يمكن فتح تفاصيلها.

| الحد | الدليل الفعلي | النتيجة |
|---|---|---|
| الواجهة → API | كتابة طلبي البدائل والضغط على الاكتشاف | كلاهما أعاد HTTP 200 و`ok` |
| API → البيانات والنماذج | استرجاع PostgreSQL وسجلات `literal_alternatives_checked: approved_v3.1` | استخدام الفرص المخزنة والنموذجين المحليين فعليًا |
| البيانات → الرد | فرصة Excel فقط، مع المصادر ونسخة الأدلة | لم نخترع SQL أو Flutter كفرصة موجودة |
| الرد → التفاصيل | فتح البطاقة ومقارنة البصمة والمصادر | تطابق التفاصيل والتوصية |
| القيود → العرض | طلب الأداتين معًا وحد ميزانية صفر | `no_match` بدل تخفيف القيود أو افتراض المجانية |
| الملف والعرض | مقارنة localStorage وفحص أخطاء JavaScript | الملف محفوظ، وصفر أخطاء غير معالجة، والأهلية غير المؤكدة واضحة |

نجحت فحوص المتصفح السبعة على وقت الطلب الحقيقي. حقل عدم التفعيل في تقرير تقييم النموذج يصف لحظة القياس؛ ملف الموافقة المنفصل يوثق التفعيل اللاحق داخل التجربة فقط. لم نجرِ نشرًا عامًا أو اختبار حمل أو توسيعًا للفرص الأربع.

[طلبات المتصفح وردوده](query-alternatives-v31-browser.json) · [التتبع وبصمات الربط](query-alternatives-v31-check.json). إعادة الفحص الاختيارية: `node scripts/verify-query-alternatives.cjs` بعد تشغيل الخدمة؛ راجع منفذ API وتواريخ العينة في دليل التجربة.
